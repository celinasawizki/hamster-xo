# Philly Hamsters 🐹🐹

A native macOS desktop pet: two animated hamsters that sit in the corner
of the desktop, interact with each other, and count down the days until
**November 6, 2026**.

Built with Swift, SwiftUI, and AppKit. No Electron, no webview, no
third-party runtime.

## Installing the app

1. Open the [Releases](../../releases) page and download `PhillyHamsters.dmg`
   from the latest release.
2. Double-click the downloaded `.dmg` to open it.
3. Drag **Philly Hamsters** into the **Applications** shortcut shown in the
   same window.
4. Open **Philly Hamsters** from Applications (or Spotlight).
5. The hamsters appear in the bottom-right corner of the screen.

No Xcode, Terminal, Homebrew, or any developer tools are needed.

**If macOS shows a warning the first time you open it** ("Philly Hamsters
can't be opened because Apple cannot verify..."), see
[Gatekeeper warnings](#gatekeeper-warnings-on-unsigned-builds) below — this
only applies to builds made without an Apple Developer signing certificate.

### Using it

- The hamsters are draggable — click and drag them anywhere on screen; they
  remember where you left them.
- Click a hamster to trigger a random reaction (jump, hug, celebrate).
- A menu bar icon (a paw print) has **Settings…**, **Reset Mascot
  Position**, and **Quit**.
- Settings lets you turn off animations, turn on sound effects (off by
  default), hide the countdown, and enable/disable launch at login.

## Building from source

Requires Xcode (the full IDE, not just Command Line Tools) and
[XcodeGen](https://github.com/yonaskolb/XcodeGen) (`brew install xcodegen`).

```sh
xcodegen generate              # regenerates PhillyHamsters.xcodeproj from project.yml
open PhillyHamsters.xcodeproj  # or build headless, see below
```

Headless build + test (what CI runs):

```sh
xcodegen generate
xcodebuild -project PhillyHamsters.xcodeproj -scheme PhillyHamsters \
  -destination "platform=macOS" CODE_SIGNING_ALLOWED=NO build
xcodebuild -project PhillyHamsters.xcodeproj -scheme PhillyHamsters \
  -destination "platform=macOS" CODE_SIGNING_ALLOWED=NO test
```

**Important:** if you add/remove/rename any Swift file, run `xcodegen
generate` again before building — the `.xcodeproj` is a generated artifact,
not something to edit in Xcode's file list directly (changes there won't
survive the next `xcodegen generate`).

## Packaging a release

```sh
./scripts/build_release.sh     # -> build/Philly Hamsters.app
./scripts/package_dmg.sh       # -> build/PhillyHamsters.dmg
./scripts/validate.sh build/PhillyHamsters.dmg
```

This produces a real, working `.dmg`. Whether it installs **without a
Gatekeeper warning** depends entirely on signing + notarization — see below.

## Signing & notarization

Distributing software outside the Mac App Store that opens with zero
security friction requires:

1. **An Apple Developer Program membership** (US $99/year) —
   https://developer.apple.com/programs/enroll/
2. **A "Developer ID Application" certificate**, created at
   https://developer.apple.com/account/resources/certificates/list and
   installed in your keychain.
3. **An app-specific password** (or App Store Connect API key) for
   `notarytool`, created at https://appleid.apple.com/account/manage.

With those in hand:

```sh
export DEVELOPMENT_TEAM="ABCDE12345"                 # your Team ID
./scripts/build_release.sh                           # builds signed

export CODESIGN_IDENTITY="Developer ID Application: Your Name (ABCDE12345)"
./scripts/codesign.sh "build/Philly Hamsters.app"

./scripts/package_dmg.sh

xcrun notarytool store-credentials "PhillyHamstersNotary" \
  --apple-id "you@example.com" --team-id "ABCDE12345" --password "<app-specific password>"
./scripts/notarize.sh build/PhillyHamsters.dmg
./scripts/staple.sh build/PhillyHamsters.dmg

./scripts/validate.sh build/PhillyHamsters.dmg
```

To run this automatically in CI (`.github/workflows/release.yml`), add
these **repository secrets** (Settings → Secrets and variables → Actions):

| Secret | What it is |
|---|---|
| `DEVELOPER_ID_CERTIFICATE_P12` | Your Developer ID cert + private key, exported as .p12, base64-encoded (`base64 -i cert.p12 \| pbcopy`) |
| `DEVELOPER_ID_CERTIFICATE_PASSWORD` | The password you set when exporting the .p12 |
| `DEVELOPER_ID_IDENTITY` | The exact identity string, e.g. `Developer ID Application: Your Name (ABCDE12345)` |
| `APPLE_TEAM_ID` | Your 10-character Team ID |
| `APPLE_ID` | The Apple ID email used for notarization |
| `APPLE_APP_SPECIFIC_PASSWORD` | App-specific password for that Apple ID |

If those secrets aren't set, `release.yml` still builds and packages an
**unsigned** `.dmg` — it just prints a warning and the resulting app will
trigger a Gatekeeper prompt. **Until signing + notarization is actually
configured and has been run successfully, don't tell the recipient the
install is completely warning-free** — point them at
[Gatekeeper warnings](#gatekeeper-warnings-on-unsigned-builds) below;
on current macOS that's a System Settings step, not just a right-click.

### Gatekeeper warnings on unsigned builds

An unsigned/ad-hoc build is still a real, functional app — Gatekeeper just
can't verify who built it, so `spctl` reports it as rejected and a plain
double-click will refuse to open it. On current macOS (tested on 26.x),
the override is a two-step flow — right-click → Open alone is often **not**
enough by itself anymore:

1. Try to open **Philly Hamsters.app** from Applications (double-click, or
   right-click → Open). macOS shows a dialog saying it can't verify the
   app, with no "Open anyway" button on the dialog itself — just dismiss it.
2. Open **System Settings → Privacy & Security**, scroll down to the
   **Security** section. You'll see a line like *"Philly Hamsters" was
   blocked to protect your Mac* with an **Open Anyway** button next to it.
   Click it, authenticate if asked, then open the app again — a final
   confirmation dialog will have a real **Open** button this time.

This is only needed once per Mac. It goes away entirely once the app is
properly signed and notarized (see above).

## Cutting a GitHub Release

1. Make sure `main` is green (Actions tab shows the Build & Test workflow passing).
2. Tag it: `git tag v1.0.0 && git push origin v1.0.0`.
3. The `Release` workflow builds, packages, (signs/notarizes if secrets are
   configured), and attaches `PhillyHamsters.dmg` to a new GitHub Release
   automatically.
4. Open the release, sanity-check the notes, and publish it (or let the
   `softprops/action-gh-release` default of a published release stand).
5. Send the release page link to whoever's getting this.

To do this manually instead: build with `scripts/build_release.sh`,
package with `scripts/package_dmg.sh`, sign/notarize/staple if you have
credentials, run `scripts/validate.sh`, then `gh release create v1.0.0
build/PhillyHamsters.dmg --title "Philly Hamsters v1.0.0"`.

## Design handoff

Character art, sprite sheets, and animation frames are specified in
[DESIGN_HANDOFF.md](DESIGN_HANDOFF.md). The app already runs on vector
placeholder drawings, so dropping correctly-named PNGs into
`PhillyHamsters/Assets/Assets.xcassets` is the entire integration step —
no engine changes required.
